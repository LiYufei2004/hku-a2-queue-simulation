# HKU A2 dual-queue choice model

Public app: https://liyufei2004.github.io/hku-a2-queue-simulation/

Passenger advisor: https://liyufei2004.github.io/hku-a2-queue-simulation/frontend/user.html

## Passenger advisor (user page)

`frontend/user.html` is a mobile-first page for people standing in the queue. It reads the current Hong Kong time. The user picks a walking speed and the queue they are in. They then tap their position on a campus map of University Street (`frontend/assets/campus-map.svg`), or choose a landmark. The page answers stay or switch, with estimated waits for both options.

On the map, the A2 lift tower stands in front of Haking Wong Building:
- The left (direct) queue runs west, past Haking Wong and along the University Street footbridge (above Kadoorie), towards the Library.
- The right (via A1) queue runs east, past Simon K.Y. Lee Hall, Composite Building and Chow Yei Ching Building, towards Jockey Club Tower.

Queue paths and landmarks live in `frontend/campus-map.js`. People counts use 0.45 m per person and are estimates: the map is simplified, not to scale. Calibrate them with `PX_PER_PERSON`, or give a landmark an explicit `n`.

The page uses the same backend and engine as the academic page, through the same API client. `backend/time-profile.js` holds the time-of-day profile:
- weekday teaching hours;
- lunch (12:00–14:00) and dinner (17:30–19:30) uplifts;
- a 10-minute peak after classes end at :50;
- lower evening, weekend and night rates.

The passenger advisor uses its own lift and arrival parameters, calibrated to the team's field measurements (CCST9017 project slides, with later corrections). The academic page keeps its defaults.
- **Direct lifts:** 15 people per full cabin, 120 s round trip (30 s dwell and 30 s travel each way), 4 cabins, giving 30 people/min.
- **Via-A1 lifts:** 200 s round trip (four 30 s stops and four 20 s legs), 4 cabins. People ride up from A1 to keep a place, so only about 4–5 board at A2, giving about 4.8 people/min.
- **Arrivals** (total, 75% at the west/direct-side entry):
  - about 25/min during lectures (measured);
  - lunch 28/min and dinner 30/min, just under lift capacity;
  - +25/min for 10 minutes after classes end at :50, so the dinner peak reaches the measured extreme of 55/min.
- With these numbers the simulation reproduces the ~80% preference for the direct lifts and a long-lasting dinner-time direct queue of about 100–200 people (observed: about 170).
- On the map, the corner from the lift door to University Street holds about 50 people (field observation); along the street the density is unchanged. `CORNER_PEOPLE` and `PX_PER_PERSON` in `frontend/campus-map.js` set this.
- In the slides, "Right" means the direct queue; this page calls it left/direct.

The user never enters the other queue. `backend/advisor.js` estimates its length from simulated snapshots that match the user's own queue at that time, `P(other | own, time)`. It then simulates staying versus walking over, using real lift events. Both pages link to each other.

## Model implemented

Version 4 uses the revised PDF walking/position-loss equations throughout the engine and conditional lookup. The interface, chart labels, status messages and exports are in English. Default entry settings: Side A 120 people/min, Side B 80 people/min, surge +60 people/min at each entry, starting at minute 0 for 10 minutes. The repeat interval remains 60 minutes because no replacement was supplied; 0 selects one surge. The defaults are illustrative inputs, not time-of-day recommendations.

The app follows the supplied Chinese PDF's three layers: NHPP entry arrivals, full-information random-utility queue choice, and empirical conditional queue-length tables for partially informed users. The old exponential half-life model and fixed-opposite-queue experiment have been removed.

### Arrival layer

Side A and Side B are independent **entry** streams, not independently assigned destination queues. Their baseline rates default to 120 and 80 people/minute. A common additional 60 people/minute applies to each entry during a default 0–10 minute class-ending window. Start time, duration, additive intensity and repeat interval are editable; interval zero means one shock. Constant baselines are placeholders for measured time-of-day curves. Rectangular shocks may overlap and then add.

Internal units are seconds and people/second. NHPP arrivals are generated by inverse integrated intensity across pulse boundaries, not by treating a time-varying rate as a constant. Twenty-Hz replay samples the exact event-driven system every 0.05 seconds.

### Choice and walking

Each entrant observes both true queue lengths and chooses left with `1/(1+exp(beta*(D_left-D_right)))`, evaluated in a numerically stable form. Beta=0 gives a 50/50 split. No explicit Gumbel sampling is necessary; this is the PDF's equivalent Logit mechanism, not a separately solved QRE equilibrium.

The decision point is the local queue tail, as in the PDF: Side A's local queue is left/direct; Side B's local queue is right/bypass. Staying has zero additional walk. Default switching distance follows the PDF: `spacing*(N_left+N_right)`, with spacing 0.45 m/person and speed 1.3 m/s. A selectable geometry comparison mode retains the earlier polyline distance at 0.025 m/pixel. These are assumptions, not measurements. Only geometry mode caps distance beyond the image; the PDF formula uses full counts. The route drawing is illustrative in PDF mode. No crowd-density slowdown is applied.

Perceived delay uses the PDF batch approximation: `walk + ceil((queue + expected_position_loss + 1)/mean_capacity) * cycle/4`. The division by four is an explicit extension for the agreed four independent lifts on each side, not a claim that the PDF includes four lifts. Expected position loss follows revised PDF equation (6): the destination queue intensity at decision time multiplied by the walking duration. Destination intensity combines both entry NHPP rates weighted by their most recent Logit split probabilities. Future surge boundaries are not integrated in this perceived-cost estimate; actual arrivals still use the exact NHPP integral. It is a local approximation, not an exact equilibrium forecast. Like the PDF, the perceived cost is conservative about services during that walk; the actual engine processes real services during it. Entrants currently walking are counted separately and join the destination queue only on arrival. Existing people in transit are not included in perceived queue length; no future random samples are revealed to deciding agents.

### Actual service

Each side has four independent batch servers, initially staggered. Mean round-trip periods are 40 seconds for left/direct and 200 seconds for right/bypass; standard deviations are 4 and 20 seconds. Periods use a truncated normal (minimum 10 seconds) rounded to 0.05 seconds. Doors are open for the last five seconds before each boarding/dispatch event. A trip's integer capacity has normal-shaped weights on max(1,C−4)…C, centered on that interval's midpoint with SD 1. Earlier user instructions remove A1 occupancy deductions. Actual service is **not** replaced by the choice approximation: each lift has its own exact scheduled event and random capacity. FIFO is based on time of joining, not original entry time.

Physical index convention: left=0=direct=PDF Queue 2; right=1=bypass=PDF Queue 1. The original background artwork has opposite legacy queue numbers; a vector annotation overlay aligns the rendered diagram with the PDF numbering. No source PDF or neighbouring course documents are published.

### Conditional decision support

The button collects exactly 1,000,000 paired `(N_left,N_right)` snapshots across independently seeded full trajectories, sampling every five seconds, with five-minute time bins. Default duration 40 minutes requires 2,084 trajectories; the final trajectory may be partial. Both origins' conditional tables use those same joint observations. The old uniform manipulation of local queue length and frozen opposite queue has been removed.

For each `(entry, time_window, observed_local_people)` condition the app stores the opposite queue's empirical histogram, sample count and sums of the two perceived delay costs. This yields `P(other_count | local_count, time_window)` and conditional mean costs including switching walk and position loss. It is valid under the full-information agents used to generate the simulation, with an occasional lookup user. Mass adoption of recommendations requires new simulations. No Bayesian/POMDP mechanism is asserted.

Lookup never reads the current hidden queue. Missing conditions are shown as missing; under 30 matching snapshots no definite recommendation is displayed. The app shows conditional cost curves instead of assuming a unique monotonic threshold. Histograms' 5–95% quantiles describe empirical queue-length variation, not confidence intervals. Correlated snapshots within a trajectory are not treated as independent Bernoulli observations for a Wilson band.

CSV and JSON downloads include the actual parameter set, seed, time-bin definition, conditional counts and means. Parameter changes invalidate the table. Times end at boarding, excluding the subsequent ride. All defaults still need field calibration.

## Running and publishing

Double-click `start.command`, or run `python3 scripts/serve.py`. `register.command` registers `~/.local/bin/comp1110-sim` without editing shell profiles. HTTP is needed for the Web Worker.

`publish.command` uses the official GitHub CLI, exports only the static assets and this README to a separate checkout, pushes main and enables GitHub Pages. Visitors do not need to log in. Subsequent runs update the same repository. The repository includes the webpage assets, model tests, local launch/registration scripts and publishing script. The export excludes local previews, generated statistics and neighbouring course documents.

## Validation

`node tests/model.test.js` checks NHPP integrals and mean counts, shock boundaries, stable Logit signs, beta=0 splitting, geometry, revised position-loss costs at surge boundaries, conditional cost aggregation, actual choice feedback, conservation including walkers, capacities, deterministic seeds and histogram normalization.

`node tests/api.test.js` checks the public interface and backend/frontend dependency boundary.

`node tests/worker-benchmark.js 1000000` runs the actual statistics worker algorithm and checks all 1,000,000 paired observations and both conditional tables. The benchmark summary is local only; it is not a precomputed lookup table shipped to users.

## Frontend / backend separation

```text
backend/
  model-core.js           # Simulation mathematics and event engine
  simulation-service.js   # Validated public operations (also usable from Node)
  worker.js               # API v1 message transport
  API.md                  # Request/response contract, units and examples
frontend/
  index.html              # English interface
  app.js                  # Playback and visualization
  batch-ui.js             # Conditional-table presentation and exports
  api-client.js           # Sole frontend transport integration point
  map-geometry.js         # Presentation-only drawing interpolation
  assets/                 # Corridor artwork
index.html                # Compatibility redirect to frontend/
tests/                    # Model invariants, API contract and worker benchmark
```

The frontend calls `generate`, `inspect`, and `collect` through
`SimulationAPI.Client`. It does not load the simulation engine or calculate
choice costs. The backend has no DOM/canvas dependency. Each client uses a Web
Worker; collection uses a separate client so it does not block replay inspection.
This is a logical computation backend hosted as static JavaScript, and does not
require a separate HTTP server. The original public root URL remains valid.

See [the API contract](backend/API.md) for exact schemas, units, cancellation,
versioning and backend-only Node.js examples. API version 1 and mathematical
model version 4 are tracked separately. The refactor preserves seeded results.
